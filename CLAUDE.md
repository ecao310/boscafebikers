## Conventions & decisions

- **Never commit the ICS URL.** It lives only in env var / GitHub secret `PARTIFUL_ICS_URL`. The script must never print it (including inside error messages — strip URLs from exception text).
- **Tests never hit the network.** Always parse `tests/fixtures/sample.ics`.
- Timezone for all displayed times: `America/New_York` (use `zoneinfo`).
- `site/` is plain static: no bundler, no build step. CSS split between shared `site/styles.css` (palette + base/nav/hero/footer — the single source for the café custom properties) and a small page-specific inline `<style>` per page. Mobile-first, warm café palette, readable at 380px. **One** exception to "no frameworks": the calendar view adopts FullCalendar 6 (MIT) from a CDN with `defer`, version-pinned with an SRI hash, with a hand-rolled fallback.
- Public Partiful profile (safe to commit, empty-state fallback): `https://partiful.com/u/Hs47uq5mucZyXLBJZCda`
- Instagram: `@bostoncafebikers`.
- Python: stdlib + the three deps above only. Script exits nonzero on fetch/parse failure.

## Gotchas

- **Default branch is `master`** — locally and on GitHub. There is no `main`; ignore any tooling that assumes one. Workflows keyed on the default branch must say `master`.
- The remote is named **`boscafebikers`**, not `origin` (`git@github.com:ecao310/boscafebikers.git`). Every push/pull spells it out.
- **Headless Chrome screenshots at phone widths lie:** `--window-size=380,…` lays the page out at Chrome's ~500px minimum window width and crops the PNG. For a real 380px layout either iframe the page at width 380 inside a same-origin harness and crop, or drive Chrome over CDP (`--remote-debugging-port=0` + `Emulation.setDeviceMetricsOverride`; node's global `WebSocket` is enough) — the CDP route also lets you call `BCB.openRideModal(ev)` and screenshot the modal.
- **Until `dev` is merged, `master` still runs the old twin workflow** (2026-08-29, expires at the merge). Two harmless consequences: (1) its `sync-dev` leg checks `dev` out and its commit step `git add`s the five data paths, which are now gitignored there — `git add` of an ignored path exits 1, so that leg goes red every 6 hours; (2) master's own `pages.yml` has no `data` checkout, so a **master**-triggered deploy publishes a `/preview/` with no ride data (the root is fine — master still carries its own committed copy until the merge). Both end the moment `dev` lands on `master`. Deploys triggered from `dev` are already correct, because `pages.yml` runs from the triggering ref.
- `ralph/ralph.log` is gitignored loop scratch — do not commit it. Detailed per-iteration notes live there; keep CLAUDE.md a concise reference. All ralph files live in `ralph/`.

## Deployment

**Live: <https://ecao310.github.io/boscafebikers/>** (also `/events.json`). Everything headless.

- **Pages source: GitHub Actions**, not "deploy from a branch" (that source only offers `/` or `/docs`; the site lives in `site/`). Check with `gh api repos/:owner/:repo/pages` (`build_type` must be `"workflow"`); set it with `gh api -X PUT repos/:owner/:repo/pages -f build_type=workflow`. The leftover `source: {branch: master, path: "/"}` is ignored — don't fix it.
- **What deploys:** `.github/workflows/pages.yml` assembles `_site/` from **three checkouts** — `master` → root, `dev` → `preview/`, and the `data` branch overlaid onto both (see the preview bullet) — uploads it via `actions/upload-pages-artifact` and publishes it with `actions/deploy-pages`.
- **The generated data lives on its own orphan branch, `data`** (2026-08-29). `events.json`, `events-past.json`, `cafe-points.json`, `rides.ics`, `maps/` and `posters/` sit at that branch's **root**, laid out exactly as they sat inside `site/`, so no published URL moved and `webcal://…/rides.ics` subscribers noticed nothing. They are gitignored on `master`/`dev`; `scripts/pull_data.sh [remote]` (`git fetch` + `git archive` of those six paths, the branch's own `README.md` deliberately left behind) pulls them into `site/` for local dev. **Why:** the two code branches used to each carry a copy, which doubled every call to Partiful/BRouter/OSM/Nominatim, interleaved ~16–20 bot commits a month into each branch's history, and collided on merge (`3833c7b`, 2026-08-23, was a hand-resolved conflict on `site/events.json`). The `github-pages` environment's branch allow-list does **not** need `data` — nothing triggered on `data` ever deploys; only `pages.yml`, running on `master`/`dev`/`workflow_call`, reads it.
- **Trigger chain — three ways in:**
  1. `push` on `master` (a human commit) → deploy.
  2. `sync.yml` (cron `0 */6 * * *` / dispatch) fetches **once**, into the `data` branch, and if its one `sync` job committed (`needs.sync.outputs.changed == 'true'`) the `deploy` job calls `pages.yml` via `workflow_call` (bot commits made with `GITHUB_TOKEN` don't fire `push`). One call rebuilds both trees, and both get the same fresh data. Dispatch on `--ref dev` to run dev's pipeline code; add `-f dry-run=true` to see what it would do without writing.
  3. `workflow_dispatch` on `pages.yml`.
  4. `push` on `dev` → same deploy, but only the `/preview/` subtree changes.
- **Redeploy by hand:** `gh workflow run pages.yml --ref master` then `gh run watch <id> --exit-status` (~15s). **Use it when a push produces no run** — seen 2026-08-26: `0453c07` reached the remote but GitHub never created the `push` run (config was fine, workflow active) — githubstatus.com showed **Actions: major outage**, which is the first thing to check (`curl -s https://www.githubstatus.com/api/v2/components.json`). Check with `gh run list --workflow=pages.yml --limit 3`; if the newest run's `headSha` isn't the pushed commit, dispatch on that branch (`--ref dev` for the preview).
- **`dev` preview: <https://ecao310.github.io/boscafebikers/preview/>** (2026-08-22). A repo has exactly one Pages site, so `dev` gets no deployment of its own: every run of `pages.yml` builds **one artifact with two trees** — `master`'s `site/` at the root, `dev`'s `site/` under `preview/` — and then overlays the `data` branch's six paths onto **both** (2026-08-29), by explicit path, so the branch's own `README.md` and `.git` never reach the artifact. That overlay is why the preview can no longer go stale between human pushes without a second sync job: root and preview read the same data commit. The root is always checked out from `master` whatever branch triggered the run, so a `dev` push cannot change the live site; no `dev` branch just means no preview. The artifact copy of each preview page gets a `<meta name="robots" content="noindex, nofollow">` injected after the **first** `<head>` (a plain substring swap would also hit `<header class="hero">`); the files on `dev` are untouched. The `github-pages` environment allow-lists deploying branches — `dev` was added with `gh api -X POST repos/:owner/:repo/environments/github-pages/deployment-branch-policies -f name=dev -f type=branch`; without it a `dev` push fails the environment gate. Preview only works because no URL in `site/` is root-relative.
- **Never use root-relative (`/…`) URLs in `site/`** — served from the `/boscafebikers/` subpath, so a leading slash 404s.
- **Sync→deploy gotchas (keep them):** `pages.yml` checks all three branches out **by name** (`ref: master` / `ref: dev` / `ref: data`), never `github.sha` — when `sync.yml` calls it, that SHA is a *code* commit and says nothing about where `data` now points. `dev` and `data` are both guarded by a `git ls-remote --exit-code --heads` check, so a fork missing either builds a smaller site instead of a red run. sync's `deploy` job carries `contents: read / pages: write / id-token: write`; the actions (`actions/checkout@v4` et al.) target deprecated Node 20 and run on Node 24 — harmless today.
- **Calendar refresh/fetch backend (2026-08-13): keep the cron.** There is no public, unauthenticated Partiful endpoint that lists an org's events (the profile page SSR carries none; its events-list callable 401s without a Firebase token), so client-side fetch can't replace the secret ICS; a serverless proxy isn't worth porting the tested parsing for marginal freshness. Public per-event pages *do* expose full data + a CORS-enabled per-event ICS (`calendarFile`) — the sync uses them to backfill ride `image` (see the "Ride photos" bullet), but they are not a feed replacement.
- `PARTIFUL_ICS_URL` **is set**; the sync bot commits real updates every 6h.

## `scripts/sync.py` — the pipeline

One process, one order, one definition of "changed". The workflow runs it as
`python scripts/sync.py --data-dir _data` (the `data` branch checked out beside
the code); locally it is `--data-dir site` after `scripts/pull_data.sh`. Either
way, run it on the fixture (never the live feed) against a **scratch copy** of
the data:

```
cp -R site /tmp/scratch-site
.venv/bin/python scripts/sync.py --data-dir /tmp/scratch-site --ics-file tests/fixtures/sample.ics
```

- CLI: `--data-dir DIR` (default `site`; `events.json`, `events-past.json`, `cafe-points.json`, `rides.ics`, `maps/` and `posters/` **all** derive from it — there is no other hard-coded `site/` in the module, which is what let the data move out of the code branches onto `data`), `--ics-file PATH`, `--now ISO` (pinned clock), `--enrich-limit N` (default 8), `--poster-limit N` (default 8), `--url-prefix` (default `maps`), `--dry-run`, and the two code-tree sidecars `--ride-images` / `--excluded-events`.
- **`--ics-file` is the offline contract**, same as `fetch_rides.py`'s: no enrichment, no geocoding, no router, no tiles — every seam is switched off, and a test booby-traps `requests.get`/`urlopen` to prove it. A test *can* have those steps offline by passing stubs to `run(config, fetch_page=…, fetch_tile=…, geocode_fetch=…)`; a seam that is handed a stub runs even on an `--ics-file` run.
- `run(config, **seams)` builds everything in memory and returns the `Run`; `FileSet` is the only writer, comparing against what was on disk when the run started, so **a file is written only when its bytes changed** and `--dry-run` can compute the whole run (later steps read an earlier step's write out of the overlay) without touching disk. Exits nonzero only on a `FeedError` / a malformed local file; an enrichment miss is soft.
- **The display fields are precomputed here, every run** — `ride_fields.derive` over the fetched upcoming list and the feed's past export (*after* enrichment, so the routes it just found get their `start_name`/`end_name`), over the merged archive, and again over the archive-backfill batch. They are a pure function of fields already stored, so no network and no backfill script: change a rule in `ride_fields.py` and the next sync re-derives every ride, upcoming and archived. `fetch_rides.py`'s and `archive_events.py`'s own CLIs derive at the same point, so a hand run and a sync run write the same bytes.
- **`run.promoted` is what makes the order matter**: it says whether `events.json` already holds *this* run's payload, and the later steps read the published list or the in-flight one accordingly. That's why reordering `STEPS` reproduces the historical bugs instead of quietly working.
- The step order is data — `STEPS`, a tuple of `(name, callable)`: **fetch → archive → enrich_archive → posters → geocode → maps → promote → export_ics** — and `tests/test_sync.py` reorders it to prove each rule (see the sync.yml section).
- **`posters` — the ride-photo mirror (2026-08-29).** Sits between the archive backfill and the maps step, and runs over the upcoming payload *and* the archive, exactly like `maps`. See the "Ride photos" bullet under `fetch_rides.py` for what it mirrors and why; the ordering rule is the maps rule verbatim — it adds `poster`, which a fresh fetch never carries, so publishing first would restamp `events.json` forever (a reordering test pins it).
- **Report and warnings (2026-08-29) — and warnings NEVER fail the job.** Every external miss here is fail-soft *and silent*: a Partiful markup change would leave every new ride with `image: null`, `routes: []`, no distance and no map, and nothing would say so. So `run()` ends by building a **`Report`** (`state.report`) counting: feed upcoming / already-happened / UIDs the exclusion sidecar caught; the upcoming list's hit rates (photo, ≥1 route, routes measured); archive size, how many were backfilled this run against `--enrich-limit`, how many are still `routes is None`; cafés looked up / found / missed this run plus placed / unplaced after it; maps drawn, rides with a route and no map, maps still without a basemap. It goes three places. **stdout**: the existing `sync:` lines plus a five-line counts block (`print_report`), and the files-written list the CLI already printed. **`$GITHUB_STEP_SUMMARY`** (appended only when the runner set it): `summary_markdown()`'s table, then the written files and the UIDs first seen this run — above the fenced stdout log `sync.yml` appends after the step, because sync.py runs first. **`sync-report.json` in the data dir**, written through the same `FileSet` so it obeys the same only-when-the-bytes-changed rule and lands in the `--dry-run` overlay. That file is subject to a hard **no-churn rule**: it must be byte-identical across two quiet runs, so `Report.state()` carries *only* sizes after the run and the fresh feed's hit rates — **no timestamp, no `now`, no "drew N / backfilled N / looked up N this run", no written-files list, no first-seen UIDs** (all of those read N on the run that does the work and 0 on the next). It is deliberately **not** added to `pages.yml`'s overlay list or `pull_data.sh` — it is not a site file; living on the `data` branch is enough, and a report-only change does produce a data commit and therefore a deploy (accepted). `Report.warnings()` returns `(level, message)` pairs printed as GitHub workflow commands under `GITHUB_ACTIONS=true` and as plain `warning:` / `notice:` lines anywhere else (`under_actions()` / `format_note()`): **warning** when enrichment ran, there is ≥1 upcoming ride and *none* has a photo (the "Partiful changed their markup" signal — gated on `enrichment_ran`, so a plain offline `--ics-file` run never cries wolf), and when the feed carried zero events at all while the archive holds ≥1 ride (the "secret rotated / feed went dark" signal); **notice** for maps still without a basemap (tile outage) and for an archive backfill queue that did **not** shrink this run (a draining queue is normal — `archive_unchecked_before` is captured in `step_archive` so only a *stalled* one is mentioned). **The project owner's rule: none of this may ever fail the job.** `main()` still returns 0, and nonzero stays reserved for a `FeedError` / malformed local file; a test runs the empty-feed warning through the CLI and asserts the exit status. The one seam this needed elsewhere is `fetch_rides.parse_events(..., skipped=)`, an optional set the pass adds the UIDs it excluded to.

## `scripts/fetch_rides.py`

Run on the fixture (never the live feed) with:

```
.venv/bin/python scripts/fetch_rides.py --ics-file tests/fixtures/sample.ics
```

- CLI: `--ics-file PATH` (bypasses the network), `--out PATH` (default `site/events.json`), `--ride-images PATH` (default `scripts/ride_images.json`), `--excluded-events PATH` (default `scripts/excluded_events.json`), `--past-out PATH` (also write the feed's already-happened rides, for `archive_events.py`; both passes share one `now`). With no `--ics-file` it reads `PARTIFUL_ICS_URL`, rewriting a leading `webcal://` to `https://`. **`--ics-file` runs never enrich** — they stay fully offline (zero network calls).
- Importable API for tests: see the function defs and docstrings in `fetch_rides.py`. Injecting `now` pins "future" without depending on the clock.
- **Never echo `requests` exception text** — it embeds the request URL. The fetch path reports only `type(exc).__name__` (+ HTTP status when present). `scrub()` strips URLs from any other surfaced text.
- Output shape: `{"updated_at", "count", "events": [...]}`; each event has `uid, title, start (ISO+offset), end (ISO+offset, may be null), date_display, time_display, location (may be null), location_hidden (bool), location_url (may be null — a maps link pasted in place of an address), description (RSVP/invite line stripped), rsvp_url (may be null), image (may be null), routes (null until enriched, then a list)`, plus the `ride_fields.derive` fields — `grace_until, place_name (may be null), address (may be null), year`, and `start_name`/`end_name` on every route. Display strings are precomputed in Python so the page doesn't render in the visitor's tz — and so that nothing it shows is re-derived in JavaScript.
- **`rsvp_url` from the feed text:** Partiful descriptions carry the event page as `RSVP: <url>` / `RSVP at <url>` / `View this event on Partiful at <url>`, line-folded across the phrase/URL boundary — `extract_rsvp_url` matches all three on the unfolded `str(event['DESCRIPTION'])`, never raw lines. `_strip_rsvp` drops the invite line from the displayed description. If there's no link at all, `derive_partiful_url` falls back to `https://partiful.com/e/<uid>` **only** for a bare UID (no `@` — descriptive `<name>@partiful.com` UIDs are never treated as ids). This is what makes the site's "RSVP on Partiful" button link to the actual event.
- **Text cleanup:** `_clean_title` strips the ` | Partiful` suffix (case-insensitive) and collapses whitespace runs, so the site shows the organizer's real name. `_clean_description` (wraps `_strip_rsvp`) additionally trims every line and collapses runs of 3+ newlines into a single paragraph break. Locations are otherwise left alone — see the hidden-location note.
- **Location:** Partiful's event model has a **single** optional Location field — there is no separate start/end location (meeting point vs. café lives in the prose DESCRIPTION instead), so `location` stays the one `LOCATION` value. When the organizer hides the address until RSVP, the export substitutes `Location available once RSVP'd`; `_clean_location` detects it (`HIDDEN_LOCATION_RE`) → `location: null` + `location_hidden: true`, and the site renders "Location shared after you RSVP"; the `.ics` download omits `LOCATION`. A Location field that holds **nothing but a link** is not an address either (2026-08-23) — the organizer sometimes pastes the meeting point's Google Maps URL there (11 archived rides did), and rendered verbatim it is an unbreakable string that overflows the card. `BARE_URL_LOCATION_RE` (`^https?://\S+$`) catches it → `location: null` + `location_url: <url>` (`location_hidden` stays **False**); prose around a link ("Meet at <url>") keeps its whole value as the location. `_clean_location` therefore returns a **3-tuple** `(location, hidden, url)` — three mutually exclusive readings of Partiful's one Location field. The card renders it as a "Meeting point on Google Maps" link and the `.ics`/Google Calendar exports put `Meeting point: <url>` in the **description**, never in `LOCATION` (calendar apps geocode a bare URL badly).
- **Excluded events (2026-08-28).** The ICS URL is the organizer's *personal* Partiful calendar export, so the feed also carries their non-ride events (a grad party, a baby shower, a birthday in New Haven…) — the first sync after the secret changed archived nine of them. They can't be told apart structurally ("We Survived!" is not a ride; "Get those Beans" is), so the organizer lists them by UID in `scripts/excluded_events.json` — a JSON object `{"<uid>": "<what it was, for humans>"}`; only the keys matter. `load_excluded_events()` (missing file → empty set; malformed / non-object → `FeedError`, like the images sidecar) feeds `parse_events(..., excluded=)`, which skips those UIDs in **both** the upcoming and the past pass, so an excluded future event can never become the home page's "next ride" either. `archive_events.py` reads the same file (`DEFAULT_EXCLUDED`, duplicated because it is stdlib-only; a test pins the two paths) and **purges** listed UIDs from the archive it already holds — adding a UID is the whole procedure for removing an event; never hand-delete from `events-past.json`, the next sync re-fills it from the feed within 6 hours. A test loads the sidecar and fails if any listed UID is still present in `site/events.json` / `site/events-past.json` — it skips on a code-only checkout, where that data has not been pulled off the `data` branch. The UID is in the ride's `rsvp_url` (`partiful.com/e/<uid>`). Orphaned `cafe-points.json` entries for an excluded ride's location are harmless (pins are drawn from the archive, not the cache) but were pruned by hand on 2026-08-28.
- **Ride photos:** the feed carries no images, so `image` has two sources. (1) **Auto-enrichment** on live-feed syncs only (added 2026-08-13): `enrich_rides()` fetches each ride's public event page at `rsvp_url` (or `derive_partiful_url(uid)`) and extracts the cover image from the page's `__NEXT_DATA__` blob (`props.pageProps.event.image`, a URL string or `{url, blurHash}`), raw Firebase-Storage-URL regex as fallback. Fail-soft: a miss leaves `image: null`, never breaks the sync. (2) The optional sidecar `scripts/ride_images.json` (UID → photo URL); an explicit sidecar entry **wins** over enrichment. A missing file or empty object just means enrichment is the only source; malformed sidecar JSON is a `FeedError` (fails loudly). Verified on `tests/fixtures/event-page.html` with a stub `fetch_page`.
- **The photos are mirrored, not hotlinked (2026-08-29).** `image` points at the original upload — a Firebase Storage URL with no resize parameter, 0.1–3.5 MB, fetched from Google by every visitor's browser. So `sync.py`'s **`posters` step** keeps a small copy: `fetch_image(url)` (a seam; `requests`, the sync's UA, 30s) downloads it, ImageMagick resizes it in a `subprocess` (**no PIL** — the stdlib-only rule holds; `magick`, else `convert`, found with `shutil.which`), and the bytes come back in memory so `FileSet` stays the only writer and `--dry-run` still writes nothing. `resize_argv(src, dst)` is a pure function a test pins: `[0]` (first frame only, so an animated source doesn't write poster-0.jpg…), `-auto-orient` **before** `-strip` (apply the EXIF rotation while it still exists), `-strip` (metadata, including the camera's GPS fix), `-resize 800x800>` (shrink only), `-quality 72`, `jpg:` output. The file is `posters/<uid>.jpg` (`render_route_maps.safe_name`, so the map and the photo share one naming rule) and the ride gains `poster: "posters/<uid>.jpg"` — a **relative** path, never root-relative.
  - **Only the organizer's own uploads.** `mirrorable(url)` is a host test: `firebasestorage.googleapis.com`, `*.appspot.com`, or `storage.googleapis.com/<bucket>.appspot.com/…` — that is where Partiful stores what the *host* uploaded. Everything else in the cover slot is artwork the organizer merely picked off a shelf, and copying it into a public repo is not ours to decide. Today's 34 rides: **20 Firebase (mirrored), 7 Partiful stock posters (`assets.getpartiful.com`), 7 Giphy GIFs (`media*.giphy.com`)** — the 14 stock ones stay hotlinked exactly as they are.
  - **`image` is never touched**; it stays the card's fallback, which is what makes every failure invisible. Three of them: **no ImageMagick on the machine** (ubuntu-latest does not ship it — `sync.yml` apt-installs it right before the sync step; the first real run without that step mirrored nothing and said so) → the whole step is skipped with a `notice:` (never a failure, never a different exit status — the owner's rule); **a definitive HTTP 4xx** → `poster: null`, the ride has had its turn and is never asked again; **anything else** (timeout, 5xx, a file ImageMagick won't read) → the key is left *absent*, so the next run retries. Absent-vs-null is the same "never checked" marker `enrich_archive` uses for `routes`.
  - **Bounded, newest-first**: `--poster-limit N` (default 8) per run, `pending_posters()` sorted on `start` descending — the same shape as the archive backfill, so ~20 archived photos fill in over three syncs instead of hammering anyone. A ride whose file already exists is **re-pointed** at it and does not count against the limit; that pass is what keeps the run-twice invariant, since the fresh feed hands the upcoming list back with no `poster` every run (the same trap `render_for_ride` avoids for `map_image`).
  - The report counts it: `posters mirrored this run` on stdout/the step summary, and `{"posters": {"mirrored", "mirrorable"}}` (sizes after the run, so no churn) in `sync-report.json`.
- **Google Maps routes (2026-08-22).** The organizer attaches the ride's route to the Partiful event as a **custom field** — a labelled link (`"Estimated Route"`, `"Team A & C Route"`, `"Start/Bluebikes"`) in `__NEXT_DATA__`'s `event.customFields`, pointing at a `maps.app.goo.gl` short link. `enrich_rides` reads them off the page it already fetches for `image` and calls `rides_routes()`, which resolves each maps-host link and keeps the ones that turn out to be **directions** (`route_from_maps_url` needs both `saddr`+`daddr`, or the `/maps/dir/A/B` path form) — that structural test is what separates a route from a "Start/Bluebikes" pin, rather than pattern-matching the label. Each entry is `{label, url, start, end, via?, points?, mode?, distance_m?, distance_display?}`; `url` is the organizer's **short link**, not the resolved one, because that's what belongs behind a button. A multi-stop route packs its waypoints into `daddr` as `"A to:B to:C"` — `end` is the last one, `via` the rest.
- **A route entered backwards is flipped (2026-08-23).** Rides always start at a Bluebikes dock, so a route whose `end` is a dock and whose `start` is not was built café → meeting point in Google Maps — the organizer did that on the Localito ride, which left the card's "from <place>" and the map's Start/End labels reversed. `orient_route()` (called at the end of `route_from_maps_url`, so `enrich_rides` and `enrich_archive.py` both inherit it) swaps `start`/`end`, reverses `via` (the last stop becomes the first) and reverses `points`; `distance_m`/`distance_display` are untouched because the ride is the same length either way. The dock is recognised structurally by `_is_bluebikes()` — the address's **first comma-segment** must start with the word "Bluebikes", so a café "near Bluebikes" is not a dock and a ride that met somewhere else (H Mart Brookline → 88 Seaport; J.P. Licks → Charles River Speedway) is never flipped. Only 1 of the 4 archived routes without a Bluebikes start actually needed it; the other 3 were already in ride order, which is why the rule tests the *end* rather than just "start isn't a dock".
- **Distance is measured, not quoted (2026-08-22).** Google publishes a route's distance only through its billed Directions API: the maps page computes it in JavaScript and the served HTML carries no number (checked — no `mi`/`km` anywhere, `<meta description>` is the generic Google Maps blurb). So the sync measures it from the *same stops Google was given*, via **BRouter** (`brouter.de`, `profile=trekking`) — a keyless public **cycling** router that also handles waypoints. The site renders `~4.0 mi`; the tilde is doing real work, since this won't match Google's figure exactly. Fail-soft: no router, no number, no broken sync.
- **Coordinates come out of the URL's `geocode=` token, not from geocoding.** Each stop has a base64 token in `geocode=t1;t2;…`; each decodes to a tiny protobuf whose field 2 (tag `0x15`) is lat and field 3 (tag `0x1d`) is lon, both `sfixed32 / 1e6`. Verified exact on all 7 real routes, including the two 4-stop team routes. **Don't replace this with Nominatim** — it resolves fewer than half of Google's free-form place strings (every "Bluebikes, Washington St at Temple Pl"-style name comes back empty), and scraping coordinates out of the maps page's minified JS is worse. `maps_geocode_points` returns `[]` unless *every* token parses, and `route_from_maps_url` only keeps `points` when there's exactly one per stop — a partial read must never yield a route that skips a stop.
- **Resolving a `maps.app.goo.gl` link needs a non-browser User-Agent.** It serves a JavaScript Firebase interstitial (HTTP 200, no target anywhere in the HTML) to browser UAs and a plain 302 to everyone else — the sync's `boscafebikers-sync/1.0` gets the redirect chain, so `_resolve_link` works with no browser. Don't "fix" that UA.
- `routes` is `None` until enrichment looks, then a **list** (empty when the event has none). The difference matters: `archive_events.merge_ride` only refuses to overwrite with `None`, so an unenriched re-export can't erase a past ride's known routes.
- **Filtering + the grace hour (2026-08-24):** a ride stays in the **upcoming** export until `start + GRACE_PERIOD` — `is_upcoming(start, now)`, `GRACE_PERIOD` (one hour) — riders turn up late and still catch the group. `past=True` is the exact complement: `parse_events` skips on the single test `if is_upcoming(start, now) == past`, so no ride can be in both files or in neither (a test sweeps −1/0/1/30/59/60/61/120 minutes around a start). Boundary **inclusive on the upcoming side** (at exactly `start + 1h` still upcoming). **Measured from `start`, never `end`:** only 6 of 40 real rides carry a DTEND and those run 3–10 hours — `max(start + 1h, end)` would pin a finished ride to the top of the page all day. The number lives **once**, as `ride_fields.GRACE_PERIOD` — `fetch_rides.GRACE_PERIOD` and `archive_events.GRACE_PERIOD` are that same object (a test asserts `is`, not `==`, so neither can quietly re-declare it), and `ride_fields.grace_until()` writes the end of the window into each ride as `grace_until`, which is what `ride-card.js` reads instead of carrying a `GRACE_MS` twin. `STATUS:CANCELLED` dropped; all-day `DATE` values become local midnight.
- The venv here is **Python 3.9**, so the module uses `from __future__ import annotations` for `X | None` hints. Keep that import.

## `scripts/archive_events.py` — past rides on the calendar

`site/events.json` is the **upcoming** list; a ride drops out of it an hour after it starts (the grace hour — see the fetch_rides filtering bullet). The calendar still shows past rides, so they accumulate in `site/events-past.json`:

```
python scripts/archive_events.py --archive site/events-past.json <source.json> [<source.json> ...]
```

- Sources are events payloads, **oldest first**. Only their already-happened rides are absorbed; the archive's own entries are never re-filtered on `now` (a clock skew must not drop history we already keep).
- **The archive keys off the same grace hour** — `is_past()` is `start + GRACE_PERIOD < now`, not `start < now`. Not optional tidiness: the sync hands this script the *previous* `site/events.json`, so a shorter rule archives a ride the fresh fetch still lists as upcoming, and `app.js` `calendarEvents()` simply concatenates archive onto events.json — the ride would render **twice**, once dimmed and once live. There is deliberately **no uid dedupe in the JS**; the invariant lives in the data. The constant is duplicated, not imported (this module is stdlib-only); tests pin `archive_events.GRACE_PERIOD == fetch_rides.GRACE_PERIOD` and run end-to-end checks at start+30m / start+90m through `merge_archive` in sync.yml's source order.
- Dedupe key: `uid`, else `start|title`. A later source wins field by field **except that `None` never overwrites a value** — that's what keeps a ride's enriched `image` after it moves into the past, since the feed's past export carries no photo and enrichment only runs on the upcoming list. The same rule carries `location_url` — an archive entry that predates the key gains it from a source, and a later export's `null` (or a source with no such key at all) never drops a link already archived; tests pin both directions.
- `run()` derives the display fields (`ride_fields.derive_all`) on the **merged** result, so whatever `merge_ride` settled on is what `place_name`/`address`/`grace_until`/`year` are computed from — a stale name can't survive a location change. Rewrites the file only when the `events` list changed (same no-churn guard as `promote_events.py`); the fields are stable across runs, so they cost one commit when they first appear and nothing after. Stdlib only; exits nonzero only on a missing/malformed source.
- **The feed carries years of past events** — the first live run archived **34**, back to 2025-09-19, not the 6 that git history had. They arrive from `--past-out` **unenriched** (only the upcoming list is enriched), so `scripts/enrich_archive.py` fills them in **newest-first, `--limit 8` per sync**: enriching 34 event pages every 6 hours would be pointless traffic for data that never changes. `routes is None` is the "never checked" marker it selects on, so once the archive is filled the step is a no-op. Result today: 34/34 have an image, 7 have route links (older rides simply had no route custom field).
- **The one thing that leaves the archive is an excluded UID** (2026-08-28): `merge_archive(..., excluded=)` drops listed UIDs from every source *and from the archive's own entries*, so `scripts/excluded_events.json` is how a non-ride is removed for good (see the fetch_rides "Excluded events" bullet). Hand-deleting from `events-past.json` alone doesn't stick — the feed still exports the event and the next sync absorbs it again; that's exactly what happened before the list existed.
- **The archive must accumulate** — don't "simplify" it into a plain past-events dump from the feed. Partiful gives no guarantee it keeps exporting old events, and once one falls out of the feed the archive is the only copy.
- `fetch_rides.py --past-out PATH` writes the feed's already-happened rides for it; `parse_events(..., past=True)` is the same parse with the filter flipped.
- Seeded 2026-08-22 from the 23 historical versions of `site/events.json` in `git log` (6 rides back to 2026-07-25), then re-cleaned through `_clean_title`/`_clean_description` and enriched — the four oldest predate the text-cleanup code, so they carried ` | Partiful` titles, the invite line, and `rsvp_url: null`.

## Route maps (`scripts/route_map.py`, `scripts/render_route_maps.py`)

Each ride's card banner is a **drawn map of its route**, not the Partiful poster (2026-08-22). `render_route_maps.py` asks BRouter for the route geometry, `route_map.py` projects it to Web Mercator and emits an SVG in the café palette, and the ride gets `map_image: "maps/<uid>.svg"`.

- **Why drawn and not a screenshot.** No browser in the sync to screenshot with; Google's Static Maps API needs a billed key; hotlinking a public tile server would aim every visitor's browser at someone else's infrastructure. So the route is drawn as SVG — and since 2026-08-23 the basemap is raster tiles embedded as data URIs in that same SVG (next bullets).
- **Basemap (2026-08-23).** `render_route_maps.py` fetches **OpenStreetMap's standard tiles** (`https://tile.openstreetmap.org/{z}/{x}/{y}.png`, 256px, keyless; UA `boscafebikers-sync/1.0`) at sync time, 2–16 per *new* ride, and `route_map.py` embeds them as `data:` `<image>`s in one `translate/scale` `<g>` in the same Mercator projection (integer tile positions inside one transform — per-tile fractional offsets leave hairline seams). Never hotlinked by the visitor's browser. **Provider is a licensing decision, not a URL:** the tiles are *stored* in committed SVGs. CARTO Positron was tried first and rejected — its Basemap Terms (§8, §9.3) require an API key and forbid storing/redistributing tile content, including as static images, so a key would not have helped. OSM's data is ODbL and its standard style is public domain; the tile usage policy asks for a unique UA, attribution clearly on the map, and no bulk downloading — the sync meets all three (a test pins the URL host + UA). osm.org/copyright does not state a separate licence for the rendered tile images, so keep the volume tiny and the credit visible. Credit line reads "Map © OpenStreetMap contributors" (`TILE_CREDIT` is `""`; the `tile_credit` param appends a provider's own line if one is ever needed), drawn at `CREDIT_SIZE` = 16 units (12 was ~4px on a phone). Tiles sit under a `WASH_OPACITY` (.42) latte wash + a bottom latte fade; labels get a foam `paint-order: stroke` halo; route casing is FOAM over tiles (OAT on the plain fallback).
- **`route_map.py` is still stdlib-only and network-free:** `tile_plan(geometry)` → `(zoom, [(x, y)…])`; the caller fetches and passes `tiles={(z, x, y): bytes}` to `render_route_svg(..., tiles=, tile_source=, tile_credit=)`, which recomputes the same plan. `fit()` exposes the projection `(scale, offset_x, offset_y, min_x, min_y)` that both `project()` and the tiles use. Tests stub `fetch_tile` with `tests/fixtures/tile.png`; a synthetic 256px palette PNG is built in-test for the crop.
- **Bytes: edge tiles are cropped, zoom follows tile side.** OSM tiles are ~30KB each and only ~40–45% of an edge tile is on the canvas, so `crop_png()` (inflate → unfilter → slice → filter-0 rows + zlib-9; OSM's tiles are 8-bit palette, non-interlaced, filter 0, sometimes several IDAT chunks — joined) trims them; anything exotic (16-bit, interlaced, not 256×256) is embedded whole. With cropping, bytes ∝ 1/(tile side)², so `choose_zoom` picks the deepest zoom with side ≥ `MIN_TILE_SIDE` (320 canvas px) — one zoom deeper = 4× bytes. Today: 55–138KB per map, ~857KB for all nine (plain maps were 6–19KB); every new ride adds 55–140KB committed forever (to the `data` branch, which can be re-rooted when that gets heavy — see the sync.yml section). **`MIN_TILE_SIDE` is the one knob**, raised 320→400 on 2026-08-24 — but don't expect a further bump to "roughly halve" it again: `choose_zoom` steps are discrete, and a route only sheds a zoom level if its tile side lands just above the floor, so most routes see no change until the floor passes ~500-600px, at real cost to legibility (neighborhood/street labels drop, not just sharpness). Don't add PIL — the crop is deliberately stdlib.
- **Fail-soft is all-or-nothing and idempotency keys on a marker.** Any missing/non-image tile → the plain latte drawing (byte-identical to the pre-basemap output) with **no** `data-basemap` attribute; `render_for_ride` skips an existing map only when `route_map.has_basemap()` sees `data-basemap="osm-standard"` on the root, so an unfinished map is retried each sync (re-fetching its 2–16 tiles until the outage clears) and rewritten only when the output differs. `--redraw` forces every map (used 2026-08-23 to regenerate the nine). The CLI prints which maps are still without a basemap.
- **Labels mirror the card (2026-08-23).** The bottom-left label uses `_start_name()` — so a Bluebikes dock reads "Start · Cleveland Circle", not "Start · Bluebikes"; the end label keeps `_place_name()` ("O'Some Café · End"). Both names now point at `ride_fields.start_name` / `ride_fields.place_name` (a test pins the identity), the same functions `derive` precomputes onto each route as `start_name`/`end_name` — one definition, and no JS twin left to keep in step. Attribute values (`aria-label`, `data-basemap`) go through `_attr()`: `xml.sax.saxutils.escape` alone leaves `"` unescaped, which made the root tag malformed for a title containing a quote.
- **Redrawing one map without `--redraw`ing all of them:** `render_route_maps.py` takes payload paths as arguments, so write a scratch payload holding just the affected ride(s) and run `render_route_maps.py --redraw --out-dir site/maps --url-prefix maps <scratch>.json` — the SVGs land in `site/maps/` and the other rides' 2–16 tiles are never re-fetched (used 2026-08-23 after the backwards-route fix). `site/maps/` is a *pulled* copy now, so a redraw meant to stick has to be committed on the `data` branch (a worktree of it is the easiest way).
- `site/maps/*.svg` are **committed on the `data` branch** (`maps/` at its root), and the render step is **idempotent** — a ride whose SVG exists *with a basemap* is skipped and only re-pointed at it, so the 6-hour sync draws only genuinely new rides.
- **The canvas shape follows the route** (`canvas_size`): height/width clamped to `[0.45, 1.0]`, so a north-south ride gets a near-square frame instead of a hairline down the middle of a letterbox. The card therefore renders map images with **`object-fit: contain`** (`.ride-img.is-map`), not the `cover` a photo gets — cropping a map loses its endpoints. Since the tiles fill the canvas the rule is `width: auto; max-width: 100%; max-height: 420px; margin: 0 auto; border-radius: 10px` (2026-08-23): full width on a phone, a tall map shrinks to 420px and sits centred on the oat card at desktop — no latte letterbox bars.
- The distance badge sits **top-left**, not centred at the bottom: a long café name in the "… · End" label ran straight over it there. It is pinned `BADGE_INSET` (16) into the corner — inside `PAD_X` and above `PAD_TOP`, so it is always clear of the route — and wears a 3px FOAM ring (2026-08-24). Before that it sat at `(PAD_X, 24)`, floating in the middle of the tile art: it clipped the route's own start dot on three of nine maps and swallowed "Cambridgeport" on another. **Tile labels land wherever OSM's renderer put them, so no inset dodges them** — an opaque pill always hides something; put it where that costs least (the corner) and make it read as a chip laid on the map (the ring, same job as the endpoint labels' halo). **`PAD_TOP` was deliberately not reduced** — it feeds `canvas_size`/`fit`, so changing it re-projects every map and invalidates all nine tile plans; the badge move is a pure overlay change, so only the four affected maps were redrawn. `fit_labels()` clips the two bottom labels until their estimated widths fit side by side.
- One scale for both axes — never stretch to fill, that would be a map that lies. `PAD_TOP` (66) reserves the badge's corner; `PAD_BOTTOM` (74) the label row.
- Feed text (title, place names) goes through `xml.sax.saxutils.escape` — same no-injection rule as the DOM.
- ODbL: the geometry is derived from OpenStreetMap, so every map carries "Route © OpenStreetMap contributors".
- `sync.yml`'s commit step **stages before diffing** (`git add -A . && git diff --cached --quiet`, inside the `_data` checkout): the maps are *new* files and a plain `git diff` doesn't see untracked ones.
- No rasterizer here, but `qlmanage -t -s 900 -o <dir> map.svg` renders an SVG to PNG so a map can actually be looked at.

## `.github/workflows/sync.yml`

Cron `0 */6 * * *` (UTC) + `workflow_dispatch`. Ubuntu, Python 3.11, pip cache keyed on `requirements.txt`, `concurrency: sync-rides` so two runs can't race a push.

- **One job, because there is one copy of the data (2026-08-29).** The `sync` job checks the code out **bare** (no `ref:` — this workflow's own ref, so the cron runs `master`'s `scripts/` and `gh workflow run sync.yml --ref dev` runs dev's), then checks the `data` branch out into `_data` (second: a root checkout wipes anything already in the workspace), runs the pytest gate, then `python scripts/sync.py --data-dir _data`, then commits **inside `_data`** and pushes. `permissions: contents: write`; plain `git push`, since `actions/checkout` leaves `_data` tracking `data`. It replaced twin `sync` / `sync-dev` jobs that each refreshed a code branch's own copy — with the data out of the code branches there is nothing to sync twice, and `.github/actions/sync-branch/` (the composite that kept the two from drifting) is deleted: with one job the "action from the workflow's ref, scripts from the branch" indirection had no purpose left.
- **Dispatch input `dry-run` (boolean, default false).** True → the sync step runs `sync.py --data-dir _data --dry-run` and the commit step is skipped (`if: github.event.inputs.dry-run != 'true'`, so a scheduled run — where the input is empty — always commits). Either way the sync step's stdout is appended to `$GITHUB_STEP_SUMMARY` in a fenced block, so the run page says what the pipeline did without anyone opening a step log — `sync.py` appends its own report table to the same file first, so the table reads above the log. `gh workflow run sync.yml --ref dev -f dry-run=true` is how a pipeline change is proved against real data before it is merged. The step captures to `$RUNNER_TEMP/sync.log` and `exit`s the script's status *after* writing the summary, so a failed run still shows its output.
- **The pipeline's first step is `python -m pytest tests/ -q`** (2026-08-29), before the fetch. It runs *the triggering ref's* `scripts/`, and `dev` is where half-finished code lives, so a branch whose scripts don't pass their own tests never gets as far as rewriting the data. Offline, so no secret and no network flake; `ci.yml` runs the same command on every push, but the cron pushes without one.
- **`deploy` gates on the one job.** `needs: sync`, `if: ${{ !cancelled() && needs.sync.outputs.changed == 'true' }}`. One `pages.yml` call republishes both trees, and both read the same `data` commit. `!cancelled()` replaces the implicit `success()` so a cancelled-then-resumed edge case can't silently skip a deploy; a failed job's output is empty, so a failure can never fake one.
- **The `data` branch can be re-rooted without touching code history.** ~4 bot commits a day land there and every new ride adds a 55–140KB map, so when it gets heavy: `git checkout --orphan data-fresh data && git commit -m "Re-root the data branch" && git push --force boscafebikers data-fresh:data`. Nothing reads its history — `master`/`dev` are the record of decisions, `data` is a snapshot of what Partiful says today. The procedure is also written on the branch's own `README.md`.
- **The pipeline is one step: `python scripts/sync.py --data-dir _data`** (2026-08-29). It used to be eight `run:` steps whose order was the only thing enforcing five rules; the order lives in `sync.py`'s `STEPS` tuple and `tests/test_sync.py` reorders it to prove each rule still bites — including the one property that had no test at all, that **a quiet sync writes zero bytes**. The reasons are still gotchas, one line each:
  - **archive before promote** — the archive is merged from the *previously* committed `events.json`, so a ride that has since started is kept even if Partiful already dropped it from the feed.
  - **maps before promote** — `map_image` is added by the map step and never by a fetch; publish first and the committed file can never equal the next fetch, so every run commits a fresh `updated_at` forever.
  - **posters before promote** — same rule for the same reason: `poster` is added by the mirror step and never by a fetch.
  - **the ICS export after promote** — `DTSTAMP` comes from `updated_at`, stamped fresh every run; exported from the fetch the calendar churns every 6 hours, exported from the published `events.json` it moves only when the rides do.
  - **the geocode step sits with the other backfills** — it reads the archive the step before just updated plus the in-flight upcoming list, so a café is placed before its ride moves into the past. It cannot churn: a location already in `cafe-points.json` (hit **or** recorded miss) is never queried again, a *transport* failure is recorded nowhere (an outage can't poison the cache; `--retry-missing` is the escape hatch), and the file is rewritten only when the mapping changed.
  - **stage, then diff** — the commit step's `git add -A . && git diff --cached --quiet`, run inside `_data`: the route maps are *new* files and a plain `git diff` doesn't see untracked ones. `-A .` on the data branch's whole tree is safe now that the tree holds nothing but data.
  - The `$RUNNER_TEMP` scratch copy is gone with the steps — the in-memory payload *is* the scratch, and `promote_events.rides_changed()` is the single definition of "did the rides change" that both `sync.py` and the standalone CLI ask. **Don't "simplify" the promote away into a fetch-in-place**: `build_payload()` stamps a fresh `updated_at` every run, so the committed file would always be dirty.
- The old per-script CLIs (`fetch_rides.py`, `archive_events.py`, `enrich_archive.py`, `geocode_cafes.py`, `render_route_maps.py`, `promote_events.py`, `export_ics.py`) are all still there and still tested — `sync.py` imports them, it doesn't shell out — so a one-off (`--redraw` a map, `--retry-missing` a café) is still a single script away.
- Committer identity is the `github-actions[bot]` noreply address.
- The secret is passed as `env: PARTIFUL_ICS_URL: ${{ secrets.PARTIFUL_ICS_URL }}` on the sync step only — never as a CLI arg (args show up in logs).
- No `yaml` module in the venv; validate the workflow with `ruby -ryaml -rjson -e 'puts JSON.pretty_generate(YAML.load_file(".github/workflows/sync.yml"))'`.

## `site/contact.html`

Its own page as of 2026-08-22; the slot it vacated on `index.html` is now the `#crew` section. Same shell as the other sub-pages (shared nav/hero/footer + page-specific inline CSS), plus a real email form and `js/contact.js` (`defer`, standalone — it does **not** touch `window.BCB`).

- **Sending, on a static site.** There is no server to POST to and nowhere to keep an API key, so "send" composes a `mailto:` and hands it to the visitor's own mail client. `contact.js` intercepts `submit`, builds `mailto:<addr>?subject=…&body=…` (message plus an `— Name <reply-to>` signature) and assigns `window.location.href`. Native `mailto:` form submission mangles the body in most browsers, which is why JS takes over.
- **Changing the address: edit `action="mailto:…"` on `#contact-form` and nothing else.** That attribute is the single source — `contact.js` parses the address out of it for both the prefilled `mailto:` and the "Prefer your own mail app? Write to …" fallback link (`#contact-direct`), and with JS off the browser still submits to that same action. Currently `boscafebikers@gmail.com` (the group's address, same as the "Other ways to reach us" card; it was the organizer's personal address until 2026-08-26).
- `#contact-direct-line` and `#contact-status` start `hidden` and are revealed by JS — no empty focusable link when JS is off (same pattern as `#updated` on the rides page).
- **Both buttons share one build (2026-08-23).** The `← Back to the ride page` link is `.btn.btn-back`; `.btn-back` rides on the `.contact-form .btn` rule (inline-flex, `min-height: 44px`, full-width below 560px / pill above — the ride-card action-row convention) and adds `margin-top: 1rem`, because `.links` is a flex box with no bottom margin and the shared inline-block `.btn` sat flush against the last card (the "isn't vertically aligned" bug). Don't drop the class back to plain `.btn`.
- Fields: name, email (`type="email"`), subject (optional → defaults to "Hello from the Boston Café Bikers site"), message. Native `required` does the validating; inputs are `font: inherit` at ≥16px so iOS Safari doesn't zoom on focus, and every control clears 44px.

## `site/cafes.html`

"Where we've been" — every café the group has ridden to, newest first (2026-08-23). Same sub-page shell as `contact.html` (shared nav/hero/footer + page-inline `<style>`), plus `js/cafes.js` (`defer`, standalone — it does **not** touch `window.BCB`, and none of the three ride scripts load here).

- **No new fetching: the data is already in `site/events-past.json`.** The page fetches the same archive the calendar dims its history with (`cache: "no-cache"`), sorts it newest-first by **lexical compare on the ISO `start`** (no `new Date()`), and renders one `.cafe` card per ride: café name, address, `date_display` **plus the ride's `year`** (`date_display` carries none and the archive spans 2025–2026; the field is precomputed by `ride_fields.derive`, with a `start.slice(0,4)` fallback), the ride title, and a "See the ride on Partiful" link (`rsvp_url`, profile URL as fallback).
- **The café name and its address are read, not split here**: `ev.place_name` (fallback `ev.location`) and `ev.address`, both written by `ride_fields.derive` — the leading comma-segment and the rest, the same rule the route labels use. `location_url` instead of an address renders the "Meeting point on Google Maps" link (same `MAPS_URL_RE` + wording as `meetingPointText()`); both null leaves no café name, so the **ride title becomes the heading** and the address line reads "Location wasn't published" (the separate title line is then omitted).
- **Grouped by `ev.year`** under an `<h2 class="year">`; the count line above the list is **computed, never hardcoded** ("34 rides to 19 named cafés and stops, since September 2025" — distinct `place_name`s, case-insensitive; 15 archived rides never published an address, hence "named"). `#cafe-count` starts `hidden` and is revealed once it has real numbers.
- **Still no thumbnails — but the reason changed (2026-08-29).** The old objection was that the real photos were hotlinked full-size Firebase originals (0.1–3.5 MB each, no resize parameter): tens of MB of someone else's bandwidth for decoration. **There is a thumbnail pipeline now** — `sync.py`'s `posters` step mirrors the organizer's own uploads as `posters/<uid>.jpg` at ≤800px, and `ev.poster` is a relative path this page could read. Adding them is a *design* decision that hasn't been taken, not a technical blocker; note that 14 of the 34 archived `image`s are Partiful stock art or Giphy GIFs and are deliberately **not** mirrored, so a grid of thumbnails would be part real photos and part stock, or would need a fallback for the ones with no `poster`.
- Fail-soft: fetch error → note + the "See all rides on Partiful" button; empty archive → its own note. Pre-JS the list holds `<p class="note">Loading cafés…</p>`. DOM via `createElement`/`textContent` only.
- **The map (2026-08-24).** `#cafe-map` sits between the count line and the list (340px, 420px from 560px up, `--radius`, oat border). It starts `hidden` and is revealed only once MapLibre has loaded, **the style JSON has been fetched** and at least one café has coordinates — a CDN outage, an unreachable tile host or an empty cache leaves no grey box, just the list (both failure paths screenshotted). **Unhide `#cafe-map` BEFORE `new maplibregl.Map()`**: a `display:none` box measures 0×0 (same trap as FullCalendar in a detached node). A WebGL-less browser throws in the constructor — caught, box re-hidden. There is no `#cafe-map-hint` any more (the organizer removed the element in 7e75c2c; the dead `getElementById` and its CSS went with it).
- **MapLibre GL JS 5.24.0 + OpenFreeMap "positron" is the site's second framework exception** (jsDelivr, version-pinned, SRI, `defer`, same shape as FullCalendar). It **replaced Leaflet + OSM raster tiles on 2026-08-24** ("red and orange highlights and hill markers … remove them"). Those were OSM standard style's trunk/primary roads and its peak/contour symbols, and **a raster tile is a finished picture — nothing can be removed from it**, which is why the fix had to be a different *kind* of basemap, not a CSS filter. Rejected on evidence: a `filter` on the tile pane only mutes (hills and every label survive); openstreetmap.de and HOT rasters still show orange motorways and "Camp Hill 16 m" on the same Boston tile; **CARTO is still out** — Basemaps ToS §3.c requires a CARTO-issued API key even free, §9.3 bans caching/proxying. **OpenFreeMap is keyless by policy, not by accident** ("no limits… no registration, no API keys, no cookies", commercial use allowed; `/styles/positron`, `/planet`, sprites and fonts all verified live). Attribution — "OpenFreeMap © OpenMapTiles Data from OpenStreetMap" — ships **inside the TileJSON**, so MapLibre prints it by default; `compact: false` keeps it as text at 380px. **Does not contradict the route-map SVG rule** (that one is about *storing* tile images in committed files). Honest cost: ~277KB gzipped vs Leaflet's ~44KB, on the one page that loads a map at all.
- **The style is filtered before the map is built** (`DROP_LAYERS` in `cafes.js`). `loadStyle()` fetches the style JSON, drops layers by id, and hands MapLibre the **object** — the layers never draw a frame (removing them after `load` would flash them first). Positron already has no motorway colour, hillshade or POI layers, so 55 → 50 removes what was left: `label_other` (**the italic neighbourhood/suburb labels** — EDGEWORTH / ALLSTON / NORTH END / SEAPORT; city and town names stay, so Boston/Cambridge/Somerville still orient you), the three route-shield layers (the US interstate badge was the last loud colour), and `airport` (a plane icon at café-pin size; Logan's runways still draw). **A style we can't fetch means no map** — `loadStyle()` returns `null` and the box stays hidden. `DROP_LAYERS` is the one knob; verified with an A/B render at identical bounds.
- **Pins are DOM markers, not a circle layer** — `new maplibregl.Marker({element})` around a real `<button class="cafe-pin">` (18px, crema fill, roast stroke, foam halo, `aria-label` = café name), so a pin is keyboard-reachable and **the colours live in `cafes.html`'s CSS** (the old `palette()` reader is gone). `scrollZoom` starts **off** and turns on at first click; rotation disabled. **One pin per coordinate, not per location string** (19 addresses → 18 pins). **The opening view ignores outliers** (`fitPoints()`: pins within `FIT_OUTLIER_DEGREES` .6 of the **median**, passed as `bounds` + `fitBoundsOptions {padding: 28, maxZoom: 15}` in the constructor so the map never flashes the whole world). **`cafe-points.json` stores `[lat, lon]`, MapLibre speaks `[lng, lat]`** — everything crossing into the library goes through `lngLat()`.
- **Popup = both halves of the question:** café name, address, one dated link per ride that ended there (`rsvp_url`; visible text is the date, `aria-label` carries the ride title), and a "Directions" link built from the **resolved coordinates**. Built with `createElement`/`textContent`, handed to `setDOMContent` as an element — never concatenated HTML. MapLibre moves focus into the popup as it opens, so `:focus-visible` rings on the popup links, pin and close button are spelled out in `var(--roast)` (the default is browser blue — the one colour the new basemap got rid of). Rides with only a `location_url` get **no pin**.
